# 业务专项 Skill：订单交易一致性检查（trade-business-check）

## 用途
针对本题（小型电商订单交易、发货与售前退款）检查跨环节业务约束是否被正确实现或被变更破坏。

## 触发场景
- 开发 Agent 完成/修改订单、库存、支付、退款、发货相关代码后自查。
- 测试 Agent 分析缺陷根因前核对业务规则。
- 验收 Agent 复核业务正确性时辅助取证。

## 输入
- 被检代码（至少包含 `internal/order`、`internal/product`、`internal/payment`、`internal/warehouse` 中的一个包）。
- `docs/01-requirement.md` 中的状态机与规则编号（R1~R8）。

## 执行步骤
1. **状态机核查**：枚举订单状态的每一次变更点，确认变更均在事务内、使用条件更新（带期望状态），不存在"直接改状态"的旁路。
2. **幂等核查**：逐项确认——支付通知重复不重复记款；同一渠道交易号唯一归属一个订单；取消/关闭不多释放库存；发货仅一次；退款仅一次（含迟到支付退款）。
3. **库存一致性**：核对"占用/释放/确认扣减"三操作是否成对出现；下单失败路径是否回滚占用；正常售前退款恢复数量、迟到支付退款不恢复数量（A5）。
4. **金额核查**：金额全部为分（整数）；退款金额等于原收款金额（整单退款）；订单保存下单时单价，不受后续调价影响。
5. **权限核查**：买家仅操作本人订单；客服/仓库/运营操作与角色匹配；身份取自 metadata 而非请求体。
6. **并发核查**：退款与发货并发、并发下单争抢最后一个名额的代码路径是否可推导出唯一合法结果。
7. 对每条检查项输出：结论（通过/违规/未执行/证据不足）、证据（文件与行号）、对应规则编号（R1~R8）。

## 输出格式
```text
[trade-business-check 报告]
- 检查范围：<文件/包列表>
- R1 库存占用：通过/违规 — <证据>
- R2 超时关闭：...
- R3 支付通知幂等：...
- R4 迟到支付：...
- R5 退款与发货互斥：...
- R6 退款结果与数量恢复：...
- R7 发货唯一性：...
- R8 记录可核查与权限：...
- 结论：PASS / FAIL（违规项列表）
```

## 失败处理
- 任一规则违规即 FAIL：列出违规项与建议修正方向，交回开发 Agent；禁止为凑通过而弱化检查。
- 无法确认时标注"需人工确认"，不得替学生下结论。

## 完成标准
八个规则项全部给出结论且有代码证据；FAIL 项在修正并复检后转 PASS。


## v2补充检查与证据边界

版本v2，2026年11月12日，基于项目原有自编草稿修订，不声称原始作者身份或创建时间已核验。原始题面和通用要求路径见docs/agents/README.md，优先读取原始来源。

输入必须包括实际提交、工作区差异或文件摘要、当前任务、AGENTS版本、相关原始输出。没有代码或服务时只能执行文件或设计审查，不能输出系统PASS。缺输入标证据不足，未执行标未执行；只有充分运行证据才可给运行验证通过。

补查付款通知由服务端在有效期内受理；恰好到期的处理记为假设，过期但关闭任务未跑不能变成合法付款。取消、超时、支付并发应裁定唯一结果。正常退款仅渠道成功才恢复数量，关闭后迟到支付退款不得再次释放。超时是结果未知，先核查原业务退款号；明确失败重试仍保持同一业务退款和整单金额上限。旧失败不能覆盖成功。

检查JWT到metadata的信任链及直连下游冒充风险，不只检查页面按钮或请求体。运营能维护商品并核查，不能直接改历史订单或删除异常。按唯一已确认收退款事实汇总，调整库存留流水；验证库存不负、占用释放一次及资金可下钻。

输出每条规则的证据文件行号、真实用例及原始结果、库存金额前后值和未验证部分。实现检查需有20请求抢5件、弃单再购、退款发货竞争、重复及越权、重启证据；静态推导不能替代这些运行结果。问题交学生指导开发，记录修正前后版本及复检，无问题保留范围而不编造缺陷。
