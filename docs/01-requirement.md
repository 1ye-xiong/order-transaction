# 题目 01 需求分析：小型电商的订单交易、发货与售前退款

> 依据《Go 项目业务场景题》题目 01 题面整理。业务规则以题面为准。

## 1. 角色与权限

| 角色 | 权限 | 说明 |
| --- | --- | --- |
| 买家（buyer，预置 3 个） | 浏览在售商品、下单（1~2 件）、付款、查询本人订单、取消待付款订单、对已付款未发货订单申请整单退款 | 身份来自登录 JWT，不能通过修改请求参数冒充他人 |
| 运营（ops） | 商品上下架、调整售价与库存、查看可售数量与交易汇总、按订单核查收款/退款/发货/异常记录 | 只读核查，不参与交易操作 |
| 仓库（warehouse） | 查询可发货订单、登记承运方与运单号完成发货（每单一次） | 发货受限：退款申请期间、已退款订单不可发货 |
| 客服（cs） | 审核售前退款（同意/拒绝并写原因）、处理迟到支付异常（发起退款）、重试失败退款 | 不能直接改订单状态消除异常 |
| 模拟支付渠道（channel 控制台） | 受理付款并发出通知、受理退款并返回结果 | 可配置行为：成功、失败、超时（不通知）、重复通知、迟到通知 |

## 2. 订单状态机

```
PENDING_PAYMENT(待付款,10min)
  ├─ 买家取消                → CANCELLED（释放占用，幂等）
  ├─ 超时（服务端时间判断）    → CLOSED_TIMEOUT（释放占用一次）
  └─ 有效支付通知（验签/匹配订单与金额/有效期内）
                             → PAID(待发货)
PAID
  ├─ 仓库发货                → SHIPPED（仅一次）
  ├─ 买家申请退款            → REFUND_REQUESTED（暂停发货）
  │     ├─ 客服拒绝          → PAID（可继续发货）
  │     └─ 客服同意 → 渠道退款成功 → REFUNDED（恢复可售数量）
  │                      └─ 渠道退款失败 → REFUND_FAILED（待客服重试，退款成功后 → REFUNDED）
  └─ (SHIPPED 后不再受理售前退款)
CLOSED_TIMEOUT + 迟到成功通知 → 订单保持 CLOSED，生成 ABNORMAL_PAYMENT 异常记录（不恢复订单、不重新占用库存）
ABNORMAL_PAYMENT → 客服发起退款 → 渠道确认 → 异常记录关闭（退款结果可查，不恢复已释放数量）
```

## 3. 主流程与规则（对应题面 8 条）

1. **商品与下单**：只能购买在售且数量足够的商品；订单保存下单时商品名与单价，后续调价不改已有订单金额；下单即占用可售数量（`可售 = 总量 − 已占用`）。
2. **超时与取消**：待付款保留 10 分钟（教学可配置缩短）；主动取消或超时关闭释放占用；重复关闭不多释放；超时判断用服务端时间。
3. **支付通知**：必须 HMAC-SHA256 验签通过、订单存在、金额匹配；重复通知不重复记款；同一渠道交易号只能归属一个订单；金额不符、未知订单、验签失败记录处理结果可查询。
4. **迟到支付**：有效期内收到的合格通知才使订单进入待发货；超时关闭后的成功通知进入异常支付待处理列表，由客服核实后发起退款，不恢复订单、不重新占用库存。
5. **售前退款**：买家对已付款未发货订单申请整单退款，申请期间暂停发货；客服同意/拒绝并写原因；拒绝后可继续发货；退款与发货并发只能形成一种合法结果（服务端事务内状态条件更新保证）。
6. **退款结果**：渠道确认成功后买家可查退款结果，正常售前退款恢复相应可售数量；渠道明确失败保留待处理记录由客服重试；迟到支付对应退款不恢复已释放数量。
7. **发货**：仓库只能为合法待发货订单登记一次发货；已发货订单不受理售前退款；不做签收/退货/售后。
8. **运营核查**：按订单查收款、退款、发货、异常处理记录；查看可售数量、已收款、已退款汇总；异常记录不能通过直接改状态消失。

## 4. 必须可演示的完整场景（验收条件）

1. **活动正常成交**：运营上架 → 买家购买付款 → 仓库发货 → 买家查运单 → 运营核查收款与库存。
2. **缺货与弃单**：20 个并发下单争抢 5 件 → 部分订单未付款超时关闭 → 其他买家购买释放的商品。
3. **售前退款**：付款后申请 → 仓库发货受限 → 客服批准 → 首次退款失败、再次成功 → 订单与数量一致。
4. **迟到支付**：订单先关闭 → 支付成功通知到达 → 客服从异常列表处理 → 运营确认无重复释放、无重复退款。
5. **操作竞争**：退款申请与发货并发、重复支付/退款通知、越权查看或处理他人订单，均有明确结果。

## 5. 数据与持久化

- 数据库：SQLite（单文件 `data/order-transaction.db`，Gorm + 纯 Go 驱动），服务重启后业务结果仍可查询；选择理由：教学环境零依赖部署、支持事务与唯一约束、单机规模足够。
- 每个服务独立建表（同库不同表）；订单域：orders / order_records（收款、退款、发货、关闭、异常处理流水）/ refund_requests / pay_exceptions；商品域：products；渠道域：channel_payments / channel_refunds。
