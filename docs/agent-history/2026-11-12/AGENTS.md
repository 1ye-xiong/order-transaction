# AGENTS.md — 题目 01：小型电商的订单交易、发货与售前退款

本文件在业务开发开始前编写，用于约束本项目内所有 AI Agent（开发、测试、验收）的行为。
业务规则以《Go 项目业务场景题》题目 01 题面为准；题面未明确的事项一律记入
`docs/01-requirement.md` 的"假设清单"，不得把猜测当成既定需求。

## 1. 三个 Agent 角色的职责边界

| 角色 | 职责 | 交接材料 | 可修改范围 | 必须先向学生确认的事项 | 禁止事项 |
| --- | --- | --- | --- | --- | --- |
| 开发 Agent | 按需求文档与任务清单实现业务代码与测试 | 需求文档、任务清单、题面 | `api/`、`cmd/`、`internal/`、`configs/`、`web/`、`docs/`、`tools/`、CI 配置 | 新增依赖、修改公共包 `pkg/`、变更数据库结构、修改题面未覆盖的业务规则 | 不得擅自扩大实现范围（如购物车、多商户、真实物流、部分退款）；不得引入题面未要求的组件 |
| 测试 Agent | 制定并执行测试，输出缺陷与复测记录 | 原始题面、被测版本的代码、需求文档 | 仅可新增/修改 `*_test.go` 与测试数据；不得修改生产代码 | 调整覆盖率排除项、修改测试超时或并发参数 | 不得通过删除失败测试、弱化断言、`t.Skip` 关键路径、排除生产代码来凑覆盖率 |
| 验收 Agent | 对照原始题面逐项验证最终版本 | 原始题面、最终版本代码、测试与部署证据 | 只读；仅可输出验收报告 | 验收结论为"不通过"时的整改建议 | 不得仅凭开发 Agent 的完成声明判定通过；不得修改任何代码 |

三个角色必须使用相互独立的会话或任务上下文。测试与验收角色必须自己读取原始题面和对应版本代码。

## 2. 仓库、分支与提交规范

- 主分支：`main`；开发分支：`dev/01`。业务代码、测试、原型、约束、Skill、配置、文档一律在开发分支提交，禁止直接推送 `main`。
- `main` 分支保护：禁止直接推送、禁止删除、禁止强推，必须通过 PR 合并并通过状态检查。
- 提交消息格式（一字不差）：`[类型] [版本号] [需求/Bug编号] 中文描述`。
  - `feat`/`fix` 提交前必须由 AI 执行 `meegle workitem get --work-item-id <数字编号> --project-key r17te9` 核验编号，并保留实际输出；未核验或核验失败不得提交。
  - 一次提交只包含一种类型；版本号格式 `v主版本.次版本.修订号`。
- 合并采用保留原始提交的方式（不用 squash 抹平历史）；合并后对主分支实际版本重新执行流水线门禁再部署。
- 部署前置门禁：格式检查、`go vet`、单元测试覆盖率 ≥85%（整体与核心业务包分别）、竞态检测全部通过。

## 3. 代码约定与数据保护

- 遵循脚手架分层：`internal/<service>` 下 `entity / model / dto / service / repo / handler`；网关在 `internal/gateway`（`request / handler / router`）；proto 在 `api/proto`，生成代码在 `api/gen`，入口在 `cmd/<service>`。
- 业务数据（订单、库存、支付、退款、发货记录）只通过服务层事务写入数据库；禁止在网关或页面直接修改数据库状态；异常记录只能由业务流程产生与关闭，不允许"直接改状态"使其消失。
- 金额一律使用人民币分（int64），禁止浮点。
- 越权控制：买家只能操作本人订单；仓库只能发货合法待发货订单；客服只处理退款与异常支付；运营只读核查。身份一律取自 JWT（网关注入 gRPC metadata `x-user-id`、`x-user-role`），禁止信任请求体中的用户编号。
- 幂等与并发：库存占用/释放、支付通知、退款、发货都必须可安全重试；支付通知签名（HMAC-SHA256）必须校验；同一渠道交易号只能归属一个订单。
- 单元测试覆盖率：整体 ≥85%，核心业务包（`internal/order`、`internal/product`、`internal/payment`、`internal/warehouse`）分别 ≥85%；并发逻辑必须有可重复执行的并发验证并跑竞态检测。
- 失败后的修正复测流程：缺陷先登记 → 开发分支修复 → 复测通过 → 重新运行受影响检查。

## 4. 假设管理

题面未明确的事项（如发货后退款边界、渠道重试次数）必须：
1. 在 `docs/01-requirement.md` 假设清单登记假设内容与依据；
2. 提请学生确认后方可实现；
3. 实现处用注释标注对应假设编号。

## 5. 真实性要求（禁止事项）

- 禁止编造接口、依赖用法、执行结果、测试报告或部署成功记录。
- 禁止伪造工作项编号或声称 meegle 核验成功。
- 禁止泄露密钥和用户敏感信息；日志、截图、对话导出须脱敏。
- AI 生成代码必须由学生检查；发现错误后保留"问题 → 修正要求 → 复测"全过程记录。

## 6. 生效与调整记录

- v1.0（开发开始前创建）：初版，覆盖以上全部条款。
- 生效方式：所有 Agent 会话开始时必须读取本文件并声明已遵守；学生抽查关键行为（如越权拒绝、提交格式）确认约束实际生效。
